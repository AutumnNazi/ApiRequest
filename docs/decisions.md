# 架构决策记录（ADR）

[English](./en/decisions.md) | 简体中文

记录关键技术选型的**决定、理由、取舍与替代方案**，以及尚待拍板的**开放问题**。决策变更时在此追加而非删除，保留演进痕迹。

状态标记：`已定` = 采纳并落入设计文档；`倾向` = 有推荐但可推翻；`待定` = 需决策。

---

## 已决策

### ADR-000 后端语言用 Go，桌面框架用 Wails v2（已定）

- **决定**：后端语言为 **Go**，桌面框架为 **Wails v2**（Go 后端 + 系统 WebView + 前端）。
- **理由**：Go 标准库对本项目核心能力覆盖度高——`net/http` + `net/http/httptrace` 提供完整网络控制与分阶段计时，gRPC 动态调用是 Go 生态一等公民；Wails 自带 Go→TS 绑定生成，前后端类型单一来源；goroutine + `context` 的并发/取消模型简单直接。
- **关键约束**：坚持**纯 Go 依赖**（goja + modernc.org/sqlite），避免 CGO，保证三平台交叉编译顺畅；禁止引入 v8go、mattn/go-sqlite3 等 CGO 依赖。

### ADR-001 桌面形态用 Wails，而非 Electron / 纯 Web（已定）

- **理由**：请求执行需绕开 WebView 的 CORS 与同源限制，并完整控制 TLS、代理、原始 Header、分阶段计时——这些只能在原生层做。Wails 用系统 WebView，包体与内存显著优于 Electron。
- **取舍**：放弃 Electron 的成熟生态与 Node 内置能力；接受各平台 WebView 差异带来的兼容成本（用 CI 三平台冒烟兜底）；自动更新链路需自建（见 OPEN-006）。
- **替代方案**：Electron（体积大）、纯 Web（受浏览器沙箱限制，无法做核心网络能力）。

### ADR-002 请求执行下沉 Go 侧（已定）

- **理由**：见 `overview.md` §2.1。原生网络控制 + 精确计时（httptrace）+ 大响应流式处理。
- **取舍**：前端无法直接发请求，所有网络操作走 Wails 绑定；换来能力与可测试性。

### ADR-003 前端框架 React + TypeScript（已定，用户确认）

- **理由**：生态最丰富、组件库多、团队熟悉度高。
- **替代方案**：Svelte / Solid（更轻但生态小），Vue（可选，用户选定 React）。

### ADR-004 集合/文件夹/请求统一为自引用树 `node`（已定）

- **理由**：移动、复制、排序、继承逻辑统一，避免三张结构相近的表。见 `data-model.md`。
- **取舍**：`kind` 字段区分类型，查询时需带类型过滤；请求专属字段存 JSON 列。

### ADR-005 请求详情存 JSON 列而非展开为表列（已定）

- **理由**：请求结构演进频繁（新增 body 类型、auth 类型、设置项），JSON 列免去频繁改表与迁移。
- **取舍**：**无法直接用 SQL 查询/索引请求内部字段**（如"所有用了某 header 的请求"）。评估认为此类查询低频，可在应用层处理，利大于弊。
- **替代方案**：全展开成列（改表频繁）、EAV 键值表（查询复杂、性能差）。

### ADR-006 主键用 UUID v7（已定）

- **理由**：时间有序，利于索引局部性与按创建时间分页；分布式生成无冲突，利于未来同步。
- **取舍**：比自增整数占空间（16 字节 vs 8），比 UUID v4 略复杂。对本地库体量可忽略。
- **替代方案**：自增整数（同步时易冲突）、UUID v4（无序，索引碎片）。Go 侧用 `google/uuid` 或 `gofrs/uuid` 生成 v7。

### ADR-007 共享类型由 Wails 自动生成 TS（已定）

- **理由**：Wails 在构建时把绑定的 Go 结构体与方法签名自动生成为 TS 类型与调用封装，前后端类型单一来源、零手写漂移，无需额外搭建类型生成流水线。
- **取舍**：生成产物形态由 Wails 决定，复杂类型（如可辨识联合 `Body`）可能需要在 Go 侧用配套的 struct/tag 表达，前端再做窄化；对无法直接映射的类型保留少量手写补充类型。
- **替代方案**：手写 TS 类型（易漂移，否决）。
- **备注**：接口契约本身已在 `data-model.md` 固定，生成机制属实现细节，Phase 1 落地时定稿。

### ADR-008 脚本引擎用 goja（纯 Go JS 引擎）（已定）

- **理由**：纯 Go 实现、免 CGO、易嵌入与沙箱化，支持 ES5.1+（含大部分 ES6），可用 `context` + `vm.Interrupt` 做超时中断。适合"每请求新建运行时"的隔离模型。
- **取舍**：性能与语言特性弱于 V8（v8go），且 v8go 依赖 CGO 会破坏交叉编译；脚本场景为轻量断言/变量处理，goja 足够。
- **替代方案**：v8go（性能强但引入 CGO，否决）、otto（更老、维护弱）。
- **沙箱约束**：禁用/不注入 `require`、文件系统、任意网络；网络仅经受控的 `pm.sendRequest` 桥接到 Go 的 http 引擎；每请求新建 goja Runtime，避免全局状态跨请求泄漏。

### ADR-009 本地存储用 SQLite（`modernc.org/sqlite`）（已定）

- **理由**：单文件、事务、成熟、易备份与迁移；配合 `blobs/` 目录存大响应体。选用 `modernc.org/sqlite`（纯 Go 实现）避免 CGO，保证交叉编译。
- **取舍**：`modernc.org/sqlite` 性能略逊于 CGO 版 `mattn/go-sqlite3`，但对本地单机负载完全够用，且免 CGO 的可移植性更重要。
- **替代方案**：`mattn/go-sqlite3`（性能好但需 CGO，否决）、自定义文件格式（重复造轮子）、嵌入式 KV（查询能力弱）。

### ADR-013 密钥存储默认系统 keychain，无可用时主密码加密回退（已定）

- **决定**：使用 `zalando/go-keyring` 访问 Windows Credential Manager 与 macOS Keychain，存放密钥变量、OAuth access token 与 refresh token；密钥本体不写入 SQLite、历史记录或集合镜像。系统 keychain 不可用时，要求用户设置主密码，以 `golang.org/x/crypto/argon2`（Argon2id）派生密钥并加密本地密钥数据。
- **理由**：默认复用 OS 已有的凭证保护与用户解锁机制，确保 Windows/macOS 一致的安全体验；回退机制使无 GUI keychain 的 CI、受限企业环境和 Linux 不阻断核心功能。
- **取舍**：首次使用回退模式须额外输入主密码；忘记主密码无法恢复密钥数据，只能清除并重新授权。
- **边界**：keychain 调用、回退存储和错误归一化只能由 `backend/secrets` 实现，业务模块不得感知具体平台后端。密钥更新与 SQLite 写入通过可回滚 Vault 批次协调：数据库失败时恢复旧值或删除新值，但不虚构跨系统的 ACID 事务。详见 [ops.md](./ops.md#1-安全考量)。

## 倾向（有推荐，可推翻）

### ADR-010 代码编辑器倾向 CodeMirror 6，而非 Monaco

- **理由**：CM6 体积小得多，对包体友好（见 `ops.md` 性能预算：单平台 < 30MB）；按需加载语言包。
- **取舍**：Monaco 的智能补全/大文件性能更强，但对本工具的 JSON/脚本编辑场景 CM6 足够。
- **翻案条件**：若脚本编辑需要接近 IDE 的补全/诊断体验，可换 Monaco 并放宽包体预算。

### ADR-011 协作同步、gRPC 排期靠后

- **理由**：先把单机体验做扎实。同步涉及冲突合并（`sync.md` 的 oplog + Lamport），gRPC 涉及 proto 动态解析，复杂度高、非核心闭环。
- **落点**：路线图 Phase 4（gRPC）/ Phase 5（同步），见 `roadmap.md`。

### ADR-012 分阶段计时用 `net/http/httptrace` 采集（已定）

- **理由**：Go 标准库 `net/http/httptrace` 提供 DNS 开始/结束、连接建立、TLS 握手、拿到首字节等回调，是采集分阶段计时的一等能力。配合 `httptrace.ClientTrace` 打点即可填满 `Timing` 各字段。
- **翻案条件**：几乎无——标准库一等能力，无自建成本。

## 待定（需决策）

### OPEN-001 是否内置 CLI 模式（无头运行 Runner）（已定：2026-07-26 落地）

- **决定**：内置 `cmd/cli`（apirequest-cli），`run` 子命令无头跑集合（数据文件/迭代/stopOnError/JSON 报告），`list` 列出工作区与集合；与桌面应用复用同一 core 与本地库；退出码 = 失败请求数（上限 100）。
- **场景**：CI 中跑集合、输出报告与退出码（类似 newman）。

### OPEN-002（已并入 ADR-013）

原"密钥存储方案"开放问题，已拍板为 [ADR-013](#adr-013-密钥存储默认系统-keychain无可用时主密码加密回退已定)。编号保留留痕。

### OPEN-003 是否支持多窗口

- **场景**：多显示器 / 并排对比请求。
- **影响**：状态管理需处理跨窗口同步（哪些 store 全局、哪些窗口内）；Wails 多窗口支持随版本演进，需确认目标版本能力。
- **建议**：v1 单窗口 + 多标签；多窗口列为后期。

### OPEN-004 集合文件镜像的目录格式规范（已定：2026-07-26 落地）

- **决定**：JSON 格式（与内部 IR 同构）；`collection.json` + 每请求单文件（`*.request.json`）+ 嵌套目录（`_folder.json`），schemaVersion 前向兼容。文件名 slug 按 Windows/macOS/Linux 的共同安全子集处理；同目录发生大小写不敏感碰撞或占用元数据文件名时追加稳定节点标识，并拒绝通过 symlink 读写镜像 JSON。见 `backend/mirror`。

### OPEN-005 许可协议

- README 中标注"待定"。开源（MIT/Apache-2.0）还是闭源，需产品层面确认。

### OPEN-006 自动更新方案（阶段性决策：仅检查与跳转）

- **背景**：Wails 无内置的签名更新链路，需要自行搭建。
- **当前决定（2026-07-31）**：发布 workflow 生成 `SHA256SUMS` 与 `update-manifest.json`；设置页只检查并打开官方 GitHub release 下载页，不执行静默二进制替换。
- **仍待定**：启用应用内更新前，必须补齐签名校验、stable/beta 渠道、原子替换与失败回滚策略。
